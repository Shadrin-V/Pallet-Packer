## Решения

- **`559`: причина не в отсутствии проверки, а в её игнорировании.** `calculateLayout` сообщает о
  непригодном вводе **значением** (`layout.errors`), а не исключением — `try/catch` там ловить
  нечего, значение надо ПРОЧИТАТЬ. Код отдельный от `ERR_VALIDATION` схемы тела: кривой JSON и
  невыполнимая заявка — разные сценарии для клиента. `422` не заводился: в кодовой базе его нет ни
  разу.
- **`s17`: импорт живёт в `SetupScreen`, не в `App`.** `initialOrders` — ЛЕНИВЫЙ монтировочный шов,
  засеять его ответом сети нельзя. Вариант «`App` ждёт импорт» отвергнут: задержал бы весь экран ради
  заказа, который может не приехать.
- **`s17`: нетронутая стартовая заготовка ЗАМЕЩАЕТСЯ** (решение владельца на финальном ревью). Иначе
  на чистом браузере пустая строка заготовки блокировала «Рассчитать» рядом с готовым заказом —
  головной сценарий фичи упирался в заблокированный расчёт. Любой реальный черновик дополняется.
- **`s17`: отдельная подсветка позиций без габаритов НЕ писалась.** Пустые размеры (не нули!) уже
  дают локальную ошибку «укажите размеры» с адресом. Живой Chrome подтвердил:
  `Berechnung nicht möglich: 1 Fehler → SO-1234 · Sonderteil ohne Masse — Maße unvollständig`.
- **Записи в `CHANGELOG` у `5iw` нет намеренно** — ни контракта, ни поведения, ни пользовательского
  эффекта. У `559` и `s17` записи есть.

## Грабли

1. **Дефект бывает в СПЕКЕ, а не в исполнении.** Финальное ревью `s17` нашло, что решение владельца
   «импорт добавляет» ломает головной сценарий на чистом браузере. Ни один тест этого не показывал —
   наоборот, тест ЗАКРЕПЛЯЛ дефект утверждением «стартовый `SO-1` на месте». Ревьюер обязан судить
   сценарий целиком, а не только соответствие плану.
2. **Караульный, которого не проверяет ни один тест, — не караульный.** `deepLinkDoneRef` держит
   однократность при зависимостях `[orders, dp]`, а `orders` меняется на каждое нажатие клавиши. При
   удалении гварда весь набор оставался зелёным: в успешном тесте `?order=` к тому моменту уже
   вычищен, в тесте ошибки `orders` не меняются. Лечится тестом с ОТЛОЖЕННЫМ промисом и правкой
   черновика при висящем запросе; необходимость доказана мутацией
   (`expected spy to be called 1 times, but got 2 times`).
3. **Комментарий, объясняющий защиту только dev-причиной, приглашает её снять.** Комментарий у
   эффекта объяснял ref через StrictMode; настоящий сценарий — прод (медленный ERPNext + правка
   черновика). Дописано.
4. **Межзадачное состояние даёт мёртвую переменную.** План завёл `importFailure` в задаче 2, а читать
   его начала задача 3 — задача 2 была вынуждена поставить первый в `apps/web`
   `eslint-disable-next-line`. Снят задачей 3. Либо не разносить состояние и его читателя по задачам,
   либо закладывать снятие в бриф следующей.
5. **`findByRole('status')` на «Настройке» неоднозначен:** там ТРИ живые области (`calcBlocked`,
   `calc-announce`, заметка импорта). Тесты ходят через `data-testid` + явная проверка атрибута роли.
   Разбор — `LKWkalk-pn0`.
6. **jsdom не заменяет браузер даже для «простого» URL-флоу.** Живая проверка через CDP (Chrome из
   `/Applications`, `--headless=new`, ~60 строк драйвера — приём из памяти `2026-08-03`) прошла 5
   сценариев и показала то, чего тесты не показывают: реальный `history.replaceState`, реальный
   `fetch`, вид заметки, и что экран сам объявляет неполные габариты импортированной строки.
   Локальный сервер требует `DB_PATH` — умолчание `/app/data/app.db` существует только в контейнере.
7. **Не выдумывай id заведённой беды.** Вывод `bd create` был обрезан, и в устном отчёте прозвучал
   несуществующий `mvy` вместо реального `LKWkalk-mcv`. Сверять `bd list`, а не память.
