# Кузов: прижать стопку к упору стрелкой (`LKWkalk-gtw`)

Ручная правка раскладки умеет двигать стопку мышью с магнитом ([ADR 020](../../adr/020-magnet-drop-resolution.md))
и группой ([ADR 021](../../adr/021-group-layout-edits.md)). Чего в ней нет — жеста «прижать»:
поставить стопку вплотную к стенке кузова или к соседу, не целясь. Магнит подтягивает к
ближайшему кандидату в пределах допуска, то есть помогает лишь тому, кто уже привёл стопку почти
на место; свободный ход в полтора метра он не проезжает.

Владелец (2026-07-30): «нужно прижать стопку к свободному краю в кузове по направлению стрелки».

## Границы задачи

- Работает **только вид сверху** и только там, где правки уже разрешены.
- Двигает то, что **выделено сейчас** — одну стопку или блок. Выделение по-прежнему мышью:
  клавиатурная навигация по стопкам в задачу не входит.
- Меняются только `x`/`y` напольной стопки. Ориентация, ярусы, вложение и `z` не трогаются.
- `clearance` не учитывается — его нет во всей алгебре правок (это `LKWkalk-qrd.31`).
- Двор склада не затрагивается: там поток с переносом, а не координаты.

## Решения брейншторма

| Вопрос | Решение |
|---|---|
| Что делает стрелка | Только до упора. Шага-нуджа и модификаторов нет — точная доводка остаётся за мышью с магнитом |
| Выделено 2+ стопок | Блок едет целиком общей дельтой, взаимная расстановка сохраняется |
| Прокрутка страницы стрелками | Стрелки перехватываются, только когда фокус в виде сверху и выделение непусто |
| Ехать некуда | Молчаливый no-op: картинка и так показывает, что стопка касается препятствия |
| Как о жесте узнают | Строка-подсказка, видимая пока есть выделение |

## 1. Ядро: `resolveSlide`

Логика хода — доменное правило («куда стопка может доехать»), а не деталь клавиатуры, поэтому
живёт в движке рядом с `resolveDrop` (принцип 1 в CLAUDE.md, [ADR 019](../../adr/019-manual-layout-editing-api.md)).

```ts
/** Ось кузова и знак хода: x — длина, y — ширина. */
export type SlideDir = '-x' | '+x' | '-y' | '+y';

/** Насколько выделенное может проехать в направлении `dir` до первого упора.
 *  Чистая и тотальная: ехать некуда, список пуст, стопки нет — `{dx: 0, dy: 0}`. */
export function resolveSlide(
  load: Load,
  layout: Layout,
  refs: StackRef[],
  dir: SlideDir,
): { dx: number; dy: number };
```

Семантика:

- **Свободный ход одной стопки** по своей оси — минимум из расстояния до стенки кузова и
  расстояний до препятствий, чья проекция на перпендикулярную ось пересекает её собственную.
  Пересечение — по полуоткрытым интервалам (`a0 < b1 && b0 < a1`), тем же правилом, что в
  `edit.ts` и `resolveDrop.ts`: соприкосновение боками не мешает проехать мимо.
- **Группа** едет общей дельтой = минимум ходов её членов; члены группы друг другу не
  препятствия. Набор исключается предикатом `exclude`, который `floorBoxes` уже принимает.
- Ненулевым может быть только компонент, отвечающий оси `dir`; второй всегда `0`.
- Целые миллиметры; функция детерминирована и не бросает.

Отдельный **запрос**, а не флаг у `moveStacks`: строгая операция судит переданную точку, а не
ищет её, и вызывающий по API/MCP должен уметь сказать «поставь ровно сюда, иначе откажи». Тот же
довод стоит в шапке `resolveDrop.ts` про `placeStack`.

Мутации новой нет: дельта применяется существующим `moveStacks`, который и валидирует результат.
Нулевая дельта до движка не доходит вовсе.

Контракт: `0.15.0` (аддитивно — новая операция-запрос и тип `SlideDir`), плюс
`docs/adr/024-slide-to-stop.md`. Оба пишутся **до** кода.

## 2. UI: `CrossSection`

Только вид сверху и только при `draggable`.

**Фокус.** Внешний `svg` (тот, что несёт `data-cutaway`) получает `tabIndex={0}` и `onKeyDown`;
при появлении выделения фокус ставится на него программно — новым `frameRef`, потому что нынешний
`svgRef` смотрит на вложенный грузовой svg. Кольцо фокуса — обычный `focus-visible`. Структура
svg и селектор `data-cutaway` не меняются, поэтому печать и экспорт PNG не затронуты.

**Клавиши.** `←`/`→` — вдоль длины (`-x`/`+x`), `↑`/`↓` — поперёк, к бортам (`-y`/`+y`).
`preventDefault` вызывается только при непустом выделении: без выделения стрелки должны
по-прежнему прокручивать страницу. `Escape` работает как раньше.

**Применение.** `resolveSlide` → дельта → существующий проп `onMoveStacks(refs, dx, dy)`, и
выделение сдвигается на ту же дельту — ровно та ветка, что уже отрабатывает групповой бросок
(`CrossSection.tsx`, ветка `onMoveStacks` в `endDrag`). Одиночная стопка идёт тем же путём:
`moveStacks` в ядре не различает 1 и N, поэтому ни нового пропа, ни нового обработчика в
`LadeplanScreen` не появляется. Нулевая дельта не зовёт ничего — выделение остаётся на месте.

**Подсказка.** Пока выделение непусто, под видом сверху видна строка `ladeplan.slideHint`
(«Стрелки — прижать к упору» / «Pfeiltasten — an den Anschlag schieben»). Экранная, `print:hidden`,
как и прочие органы правки. Ключ добавляется в `packages/i18n` для `de` и `ru`.

## 3. Тесты

Ядро — `packages/engine/src/packing/resolveSlide.test.ts`:

- одинокая стопка едет до стенки в каждом из четырёх направлений;
- упор в соседа: стопка встаёт вплотную, зазора не остаётся;
- сосед, чья проекция на перпендикулярную ось не пересекается, ход не ограничивает;
- ближайший из двух препятствий и определяет ход;
- группа едет по минимуму ходов членов; сосед внутри группы ход не ограничивает;
- стопка уже вплотную → `{0, 0}`; пустой список → `{0, 0}`; несуществующий `ref` → `{0, 0}`;
- после применения дельты через `moveStacks` валидатор геометрии не находит ни пересечений, ни
  выхода за габариты.

UI — `apps/web/src/screens/components/CrossSection.test.tsx`:

- стрелка при выделенной стопке зовёт `onMoveStacks` с ожидаемой дельтой, выделение сохраняется;
- без выделения стрелка не зовёт ничего и не давит прокрутку (`defaultPrevented === false`);
- в виде сбоку стрелки не делают ничего;
- подсказка видна при выделении и исчезает без него.

Слабый тест ловится вырожденной заглушкой: `resolveSlide`, возвращающий нули всегда, обязан
валить тесты «едет до стенки» и «встаёт вплотную» — поэтому они утверждают КОНКРЕТНУЮ дельту,
а не «дельта ≥ 0».
