# Транспорт с несколькими грузовыми отсеками — автопоезд (`LKWkalk-p3p`)

Со схемы логиста ([справочник](../../lkw-presets-logist-2026-07-20.md), вариант 5) есть автопоезд:
15 400–16 000 мм при ширине 2450 и высоте 3050, 110–120 м³. Внести его пресетом сегодня нельзя:
`Vehicle` — это одни внутренние размеры, поэтому единый отсек длиной 15,4 м разрешит упаковщику
поставить поддон **в разрыв между тягачом и прицепом**, где нет пола. Вариант 5 по этой причине был
осознанно отложен владельцем 2026-07-20 и ведётся этой задачей.

Нужна модель нескольких грузовых отсеков — сквозная: упаковщик, метрики, ручная правка,
визуализация, отчёт.

## Решения брейншторма (2026-08-04)

| Вопрос | Решение владельца |
|---|---|
| Что делает «Рассчитать» для автопоезда | Одна заявка, **движок сам делит груз** между кузовами; результат — один план |
| Может ли заказ (`orderId`) разъехаться по двум кузовам | **Может, если не влез** целиком: сначала пробуем один кузов, хвост уходит в соседний |
| Ручная правка при двух кузовах | **Внутри отсека**; перекинуть стопку между кузовами — через двор (снять → поставить) |
| Длины отсеков | **7700 + 7700** сейчас (Jumbo-Gliederzug, сходится с 15 400 мм и 110–120 м³); помечено как требующее подтверждения логистом |
| Редактор кузова | **Поле длины на каждый отсек**; ширина и высота общие; добавлять/удалять отсеки нельзя |
| Чертёж | **Один рисунок с видимым разрывом**, а не блок на каждый кузов |

## Границы задачи

- Отсеки различаются **только длиной**: ширина и высота — общие, у `Compartment` их нет вовсе.
  Разные сечения у отсеков одного транспорта в эту модель не заложены; понадобятся — отдельное решение.
- Добавление и удаление отсеков в редакторе не делается: пресет задаёт их число, пользователь правит длины.
- Перетаскивания стопки между кузовами жестом нет (решение владельца).
- Вес, нагрузка на оси, распределение по осям — вне MVP, как и было.
- Трёхзвенные составы модель выдержит, пресета для них не будет.
- `clearance` в алгебре правок по-прежнему не участвует (`LKWkalk-qrd.31`).

## 1. Модель: отсеки как интервалы на общей оси длины

```ts
/** Грузовой отсек — интервал [x, x + length) на оси длины транспорта. */
export interface Compartment {
  id: string;
  /** Ключ метки; локализация — на стороне UI. */
  name?: string;
  /** мм, начало отсека по оси длины; >= 0, целое. */
  x: number;
  /** мм, > 0, целое. */
  length: number;
}

export interface Vehicle {
  id: string;
  name: string;
  /** мм — полный пролёт по длине, ВКЛЮЧАЯ разрывы между отсеками. */
  length: number;
  width: number;
  height: number;
  /** Отсеки по возрастанию `x`. Отсутствует = один отсек [0, length). */
  compartments?: Compartment[];
  maxPayload?: number;
}
```

Автопоезд: `compartments = [{x: 0, length: 7700}, {x: 8900, length: 7700}]`, `length = 16600`.
Интервал 7700…8900 — физический разрыв между машинами: координаты там существуют, груз туда не встаёт.

**Сквозной инвариант, заменяющий проверку габаритов:**

> Единица груза лежит целиком внутри **одного** отсека. Не «в габаритах кузова» — в габаритах отсека.

Он запрещает и постановку в разрыв, и стопку, оседлавшую границу машин. Проверяется там же, где
сегодня стоит проверка границ: `findGeometryViolations`, `edit`, `resolveDrop`, `resolveSlide`.

### Почему интервалы, а не `compartmentId` с локальными координатами

Альтернатива — дать `Placement` и `StackRef` идентификатор отсека и считать координаты от угла
каждого отсека.

| | Разрыв на общей оси | `compartmentId` + локальные координаты |
|---|---|---|
| `Placement`, `StackRef`, `PlaceStackSpec`, `DropResolution`, `GroupAim`, `SlideDelta` | не меняются | у каждого появляется отсек |
| Контракт | **аддитивно, 0.16.0** | ломающее: мажорная версия + синхронная правка всего UI |
| Пиксельная математика UI | не меняется | переписывается |
| Выбранный чертёж «один рисунок с разрывом» | получается сам собой | надо собирать N вложенных svg |

Решающий довод — устройство чертежа. Область броска в `CrossSection` — это **одна вложенная**
`<svg data-hold>` с `viewBox="0 0 length spanY"`; через `getScreenCTM` она отображает клиентские
пиксели прямо в миллиметры груза, и `LadeplanScreen` пересчитывает через неё же броски из двора в
кузов. Пока ось длины одна, `toSvg`, призрак переноса, бросок двор→кузов, PNG-экспорт и линейка не
трогаются вовсе. Локальные координаты потребовали бы N таких svg и переписывания всей этой
математики — ради данных, которые упаковщику всё равно не нужны.

Задача поэтому **перестаёт быть ломающим изменением контракта**, вопреки исходной формулировке в
`bd` и в справочнике пресетов. Это фиксируется в ADR 026.

Разрыв (1200 мм) влияет только на пропорции картинки: упаковщик его не видит, ни одна метрика его не
учитывает. Как и длины 7700, он помечается в доках как требующий подтверждения логистом.

### Побочный эффект: метрики перестают врать

Сегодня объём кузова — `length × width × height`. С разрывом это завысило бы кузов на пустоту,
занизив `volumeFillPercent`. Площадь пола и объём считаются суммой по отсекам:

```
floorArea  = Σ (отсек.length × width)
holdVolume = floorArea × height
```

Для односоставного кузова обе формулы дают ровно прежнее число.

## 2. Упаковщик

Внешний цикл по отсекам; внутри — сегодняшняя логика зон заказов без изменений.

```
для каждого отсека (в порядке x):
    region = { length: отсек.length, width }     ← ровно то, что packFloor умеет сейчас
    зоны заказов раскладываются срезами внутри отсека (xOffset стартует с отсек.x)
    остаток количеств переходит в следующий отсек
```

Единственная структурная правка в `packages/engine/src/packing/orchestrator.ts`: карта `remaining`
сегодня рождается и умирает внутри одного прохода `packZones` — её нужно протянуть сквозь отсеки,
чтобы прицеп знал, чего не хватило тягачу. `packFloor`, `computeVerticalStack` и `columnPlacements`
не трогаются: они и так пакуют прямоугольную область.

Следствия, каждое под тестом:

- **Приоритет заявки сохраняется.** Голова списка `cargo` грузится в первый отсек, хвост уезжает в
  следующий; под давлением места в `unplaced` уходит конец списка ([ADR 017](../../adr/017-dense-floor-heuristic.md)), а не самые мелкие.
- **Заказ продолжается в соседнем кузове**, если не влез целиком. Внутри каждого кузова он
  по-прежнему смежная зона ([ADR 011](../../adr/011-order-grouping.md)).
- **`fill` работает в обоих кузовах**: «сколько влезет» — остаток первого отсека плюс остаток второго.
- **`densityFirst` не меняет смысла** ([ADR 016](../../adr/016-order-grouping-density-toggle.md)):
  сравнение «strict против одной области» остаётся, просто каждый из двух вариантов считается по
  всем отсекам.
- **Детерминизм.** Порядок отсеков — по `x`; стохастики не добавляется.

**`Layout` не меняется ни на поле.** Счётчики «в тягаче 41, в прицепе 38» UI получает, разложив
`placements` по интервалам отсеков; хранить их в контракте незачем. Это и есть выигрыш общей оси.

## 3. Валидация

Новый код ошибки — один:

| Код | Условие |
|---|---|
| `ERR_INVALID_COMPARTMENTS` | `compartments` присутствует, но пуст; `x` или `length` не целые, `length ≤ 0`, `x < 0`; отсеки не по возрастанию `x` или пересекаются; конец последнего ≠ `vehicle.length` |

Требование «конец последнего = `vehicle.length`» держит `length` честно производным и не даёт
завестись молчаливой мёртвой зоне в хвосте. Пустой массив невалиден намеренно: односоставный кузов
выражается **отсутствием** поля, чтобы у одного состояния не было двух представлений.

`ERR_CARGO_EXCEEDS_VEHICLE` меняет смысл: груз великоват, если не влезает **ни в один** отсек в
любой разрешённой ориентации. Восьмиметровая деталь в автопоезд 2 × 7,7 м не помещается, хотя
формально короче полного пролёта 16,6 м.

## 4. Ручная правка, магнит, упор

Ни одной новой операции и ни одного нового кода ошибки. Меняется одна проверка — та же, что в §1.

- **`moveStack` / `placeStack` / `moveStacks`.** Проверка «влезает ли в `vehicle.length × width`»
  становится «влезает ли целиком в какой-нибудь отсек». Отказ идёт существующим
  `ERR_EDIT_OUT_OF_BOUNDS`: для пользователя «сюда нельзя» одинаково на краю кузова и на краю сцепки.
- **Магнит `resolveDrop`** ([ADR 020](../../adr/020-magnet-drop-resolution.md)). Кандидаты-стенки
  `0` и `length − dx` заменяются стенками **каждого** отсека; позиции впритык к соседям остаются как
  есть. Правило выбора не меняется (больше «впритык»-осей → ближе к прицелу → `(x, y)` по
  возрастанию). Разрыв не требует особого случая: позиция в нём не лежит целиком ни в одном отсеке и
  в кандидаты не попадает. Побочно прицел **в разрыв** примагничивается к ближайшей стенке соседнего
  кузова, если попал в `tolerance`.
- **Упор `resolveSlide`** ([ADR 024](../../adr/024-slide-to-stop.md)). Упор — стенка своего отсека.
  Стопки за разрывом не помеха и не цель. Групповой ход остаётся минимумом ходов участниц, поэтому
  выделение по обе стороны разрыва упрётся в первую же стенку и через него не переедет — «внутри
  отсека» получается само, без запретов в коде.
- **Двор.** `stackBuffer` не трогается. Бросок из двора в разрыв ведёт себя как бросок мимо: ядро
  отвечает отказом, призрак красный.

## 5. Контракт

Версия **0.16.0**, аддитивно: добавлены тип `Compartment`, поле `Vehicle.compartments`, код
`ERR_INVALID_COMPARTMENTS`; переформулирован инвариант границ (отсек вместо кузова) в описании
`findGeometryViolations` и операций правки. Формы `Placement`, `StackRef`, `PlaceStackSpec`,
`Layout`, `DropResolution`, `SlideDelta`, `BufferStack` не меняются. Отсутствие `compartments` = один
отсек = сегодняшнее поведение, побайтово.

## 6. Экран

**Лист плана.** Обе фигуры (сбоку и сверху) сохраняют нынешнее устройство: их `viewBox` уже растянут
на всю длину. Добавляются толстые стенки на границах отсеков, разрыв рисуется как «не кузов» (без
пола и сетки), подписи отсеков и счётчики размещённого под каждым. `toSvg`, бросок двор→кузов через
`data-hold`, PNG-экспорт и линейка не трогаются.

**Настройка.** Для многосоставного кузова вместо одного поля длины — поле на каждый отсек; ширина и
высота общие. Объём в сводке (`setupValidation`) считается суммой отсеков.

**Пресет.** `Автопоезд (Jumbo)`: два отсека 7700 × 2450 × 3050, разрыв 1200, ключи меток в `de` и `ru`.
После него в справочнике пресетов снимается пометка «вариант 5 не вносится».

### Два признанных хвоста

1. **Обвес прицепа.** `truckChrome` рисует кабину и ходовую одной машины. В этой задаче — скупо и
   геометрически честно: ходовая под вторым кузовом, дышло в разрыве. Полноценная иллюстрация
   прицепа заводится отдельной задачей в дизайн-эпик `LKWkalk-41e`, где уже лежат брифы на
   rigid/semitrailer/swapbody, а прицепа среди них нет.
2. **375 px.** Состав 16,6 м в одну строку мельче, чем 13,6 м, — это цена общего чертежа, выбранного
   владельцем. Проверяется живьём в Chrome на 375 px до мержа. Если нечитаемо — факт выносится
   владельцу, компоновка молча не меняется.

## 7. Тесты (ведущие, до кода)

- Точный ответ: кузов из двух отсеков 2400 × 2400 × 2400, груз 1200 × 1200 × 1200 → ровно 8 напольных
  мест, по 4 в отсеке.
- **Ни одна единица не попадает в разрыв** — property-тест поверх `findGeometryViolations` на
  случайных заявках.
- Стопка, оседлавшая границу машин, отвергается валидатором, `placeStack` и `moveStacks`.
- Магнит: прицел в разрыв примагничивается к ближайшей стенке соседнего отсека; за пределами
  `tolerance` — отказ.
- Упор: выделение по обе стороны разрыва не переезжает через него.
- Заказ, не влезший в первый отсек, продолжается во втором (решение владельца из §2).
- `fill` заполняет оба отсека.
- Валидация: каждый пункт `ERR_INVALID_COMPARTMENTS` по отдельности; груз, влезающий в пролёт, но не
  в отсек, даёт `ERR_CARGO_EXCEEDS_VEHICLE`.
- **Регрессия аддитивности:** односоставный кузов без `compartments` даёт тот же `Layout`, что
  сегодня. Это главный страховочный тест — он и доказывает, что изменение не ломающее.

## Открытое, требующее подтверждения логистом

Числа ниже правдоподобны и согласованы со схемой, но не сняты с реальной машины. Помечены в пресете
и в справочнике; при получении точных значений правятся одной строкой, ни модель, ни код не
затрагивая.

- Длины отсеков 7700 + 7700 (Jumbo-Gliederzug; сходится с 15 400 мм и 110–120 м³ со схемы).
- Разрыв 1200 мм — только пропорции чертежа, на расчёт не влияет.
- Вариант 16 000 мм со схемы — вероятно 7700 + 8300; заводится пользователем правкой полей длины.
