# Уникальность `cargo.id` в `validateLoad` (LKWkalk-p3p.15)

Дата: 2026-08-05 · Статус: утверждён владельцем · Контракт движка `0.17.0` → `0.18.0` (аддитивно, ADR не нужен)

## Задача

`validateLoad` не отвергает `Load`, в котором два элемента `cargo` делят один `id`. Дыра давняя и не
регресс ветки `p3p`: движок группирует `placements`/`unplaced` по `cargoTypeId`
(`api.ts` → `getLayoutReport`, `metrics.ts` → колонки, `orchestrator.ts` → остатки по типу), поэтому
второй элемент с тем же id портит счётчики первого — «запрошено/размещено/не размещено» врут молча,
без единого сообщения.

Второй вход у задачи появился в `p3p`: `compartmentErrors` уже проверяет уникальность `id` отсеков
(`duplicateId`), и для груза симметрично напрашивается такая же проверка.

Откуда дубль может прийти на практике: `id` позиции в SPA — `crypto.randomUUID()`
(`setupState.emptyPosition`), так что из интерфейса дубли не рождаются. Реальные входы — испорченный
вручную черновик в `localStorage` (`loadSetup` уникальность не проверяет), клиенты серверного API и
будущий MCP. Контракт защищается на границе ядра, а не на каждом входе по отдельности.

## Решения владельца

1. **Защита живёт только в ядре.** `validateLoad` отвергает `Load` кодом `ERR_DUPLICATE_CARGO_ID`.
   Самолечение черновика в `loadSetup` (перевыдача uuid при загрузке) отвергнуто: оно прячет порчу
   данных и оставляет второй скрытый путь правки состояния, а внешние входы всё равно требуют
   проверки в ядре.
2. **По одной ошибке на каждый задвоенный `id`**, а не одна на весь `Load` (как у отсеков) и не по
   одной на каждое повторное вхождение. `cargo` — пользовательская заявка из многих строк, и
   остальные её проверки построчные; владелец должен увидеть все сломанные id за один прогон, а не
   чинить их по одному. Повторные вхождения не различаются адресом (`addressOf` хранит один адрес на
   `id`), поэтому дробить сообщение до вхождения незачем.
3. **Текст говорит и что сломано, и что делать:**
   - de: `Zwei Ladungspositionen haben dieselbe interne Kennung. Bitte die Zeile löschen und neu anlegen.`
   - ru: `Две позиции заявки имеют одинаковый внутренний идентификатор. Удалите строку и создайте её заново.`

   Слово «внутренний» честно помечает сбой данных, а не ошибку ввода: пользователь `cargo.id`
   никогда не видел. Формулировка «эта строка задвоена» отвергнута как неточная — строки могут
   отличаться именем и габаритами, совпадает только `id`.

## Дизайн

### Проверка в ядре

`packages/engine/src/validation/codes.ts` — новый член `VALIDATION_ERROR_CODES`:

```ts
'ERR_DUPLICATE_CARGO_ID',
```

`packages/engine/src/validation/validate.ts` — отдельный проход по `load.cargo` до построчного цикла:
считаем вхождения каждого `id`, затем идём по `cargo` в исходном порядке и выпускаем ошибку **на
первом вхождении** каждого id со счётчиком ≥ 2.

```ts
{ code: 'ERR_DUPLICATE_CARGO_ID', details: { cargoTypeId: c.id, count } }
```

**Место в списке ошибок фиксировано:** после `ERR_EMPTY_LOAD`, до построчного цикла. Сначала
претензии к кузову и к заявке целиком, потом к отдельным строкам. Порядок — не вкусовщина: от него
зависит, к какой строке прыгает «Рассчитать» (`firstError`), и плавающий порядок означал бы разный
прыжок на одном и том же вводе.

**Сравнение точное, без `trim`** — намеренно иначе, чем у локальной проверки `duplicateOrderId`
(`setupValidation.setupMessages`), где `«SO-1»` и `« SO-1 »` считаются одним заказом. Для движка `id`
— ключ группировки как есть: `"a"` и `" a "` дают разные колонки, разные строки отчёта и разные
остатки, то есть работают корректно. Ругаться на них означало бы отвергать законный ввод.

**Дубль ничего не подавляет.** Совпадение `id` не говорит ничего о габаритах, вращении и вложении,
поэтому построчные коды (`ERR_INVALID_DIMENSION`, `ERR_CARGO_EXCEEDS_VEHICLE`, …) по тем же строкам
остаются. Единственное существующее подавление внутри `validateLoad` — гейт `vehicleValid &&
dimsValid && …` перед `ERR_CARGO_EXCEEDS_VEHICLE` — не трогаем.

### Что закрывается дальше по цепочке

Кода вне `validation/` не пишем — уже готовые механики срабатывают сами:

- `calculateLayout` при непустом `validateLoad` возвращает пустой `Layout` с `errors` и до упаковщика
  не доходит (`api.ts`), поэтому испорченные счётчики просто не создаются;
- предохранитель в `App` (p3p.16) не пускает layout с `errors` в состояние ни при расчёте, ни при
  восстановлении из `localStorage`.

### Экран «Настройка» — правок кода нет

`engineMessages` адресует строке **любой** код, у которого в `details` есть `cargoTypeId`, через
карту `addressOf`. Новый код получает адрес, счётчик `setup.header.calcBlocked` и прыжок
«Рассчитать» бесплатно. Две границы честности, обе приняты осознанно:

1. **Адрес ведёт к последнему вхождению.** `addressOf.set(p.id, …)` перезаписывается, так что из двух
   строк с одним id подсветится вторая. Ошибка чинится удалением любой из них, поэтому уточнять адрес
   до первого вхождения незачем.
2. **Локальная ошибка на той же строке глушит этот код** — общее правило `allMessages` (p3p.16).
   Испорченный черновик, где задвоенная строка ещё и недозаполнена, покажет «укажите размеры» вместо
   сообщения о дубле. Расчёт при этом всё равно заблокирован локальной ошибкой: молчаливого успеха
   не возникает, а после дозаполнения строки код о дубле проявится.

Оговорка из спеки p3p.16 («карта `cargoTypeId → where` при дублях сохранит один адрес из двух, и
точной адресации спека не обещает») этой задачей **снимается по существу**: дубль теперь сам является
ошибкой, а не молчаливым состоянием.

## Тесты

Движок (`validation/validate.test.ts`):

- два `cargo` с одним `id` → ровно одна ошибка `ERR_DUPLICATE_CARGO_ID`, `details.count === 2`;
- три `cargo` с одним `id` → по-прежнему одна ошибка, `count === 3`;
- два разных задвоенных id → две ошибки, в порядке первых вхождений;
- `id`, различающиеся только пробелами (`"a"` / `" a "`) → кода нет (закрепляет отказ от `trim`);
- валидная заявка без дублей → кода нет;
- дубль не отменяет построчные коды: задвоенная строка с нулевой высотой даёт и
  `ERR_DUPLICATE_CARGO_ID`, и `ERR_INVALID_DIMENSION`.

Экран (`setup/setupValidation.test.ts`): черновик с двумя позициями одного `id` даёт сообщение
`ERR_DUPLICATE_CARGO_ID` уровня `error` с адресом на строку.

Контракт: `packages/engine/src/index.test.ts` — `0.18.0`.

**Мутационное доказательство обязательно для каждого нового теста** (урок p3p.16): убрать
проверяемую строку производственного кода → увидеть FAIL → вернуть → увидеть PASS, вывод обеих
команд показать в отчёте. Особый риск здесь — фикстура, которая не доводит до проверяемой ветки:
дубль на позициях с `quantity: 0` до движка не доедет вовсе (`toCargoList` их отбрасывает), а
задвоенная строка с локальной ошибкой будет заглушена в `allMessages`.

## Не входит

- Самолечение черновика в `loadSetup` (решение 1);
- серверная граница — `POST /api/plans` сохраняет план с `layout.errors` как успешный
  (`LKWkalk-559`, отдельная задача);
- перевод группировки `placements`/`unplaced` с `id` на индекс позиции — это переписывание счётчиков,
  метрик и легенды, отдельный эпик.
