# Коды валидации движка на экране «Настройка» (LKWkalk-p3p.16)

Дата: 2026-08-05 · Статус: утверждён владельцем · Контракт движка не меняется (ADR не нужен)

## Задача

SPA нигде не рендерит `Layout.errors`. Нажатие «Рассчитать» с невалидным вводом — длина отсека 0
(`ERR_INVALID_COMPARTMENTS`), груз не влезает ни в одной разрешённой ориентации
(`ERR_CARGO_EXCEEDS_VEHICLE`) — молча даёт пустой план без объяснения причины. `errorCount` в шапке
считает локальные UI-проверки (`setupMessages`), а не коды движка: это разные множества ошибок.

Корень шире, чем «не рендерим». Груз для расчёта собирается **в двух местах** — в `handleCalculate`
и в Demo, — и ничто не мешает им разойтись; валидации нужен третий такой же. Плюс `App` принимает
layout с ошибками как успешный результат, поэтому дыра воспроизводится и в обход экрана.

## Решения владельца

1. **Живая валидация.** `validateLoad` вызывается на каждый рендер рядом с `setupMessages`, из того
   же состояния. Коды движка становятся обычными сообщениями панели: считаются в `errorCount`,
   кликаются, «Рассчитать» прыгает к первой. Ошибка видна ДО нажатия.
2. **Локальная ошибка глушит коды движка на той же строке.** Недозаполненная строка даёт одно
   человеческое «укажите размеры», а не три `ERR_INVALID_DIMENSION`.
3. **Обратное глушение — ровно одна явная пара:** `ERR_CARGO_EXCEEDS_VEHICLE` прячет `tooTall`.
   Общее правило «ошибка движка съедает warning строки» отвергнуто: `duplicateOrderId` относится к
   заказу, а адресован строке, и случайная ошибка движка на этой строке проглотила бы его.
4. **«Рассчитать» отказывает при любой ошибке.** Есть адрес — переход к строке (как сейчас); адреса
   нет — фокус в панель сводки и объявление в живую область.
5. **Нулевые позиции не попадают в `Load`.** `quantity === 0` — законный способ временно исключить
   строку (§6), поэтому её габариты не должны блокировать расчёт. Сегодня блокируют молча: движок
   проверяет вписываемость независимо от количества.
6. **Локальные ошибки строки блокируют расчёт независимо от количества.** Обнуление исключает строку
   из груза, но не отменяет незаконченную работу: недозаполненная строка требует дозаполнить или
   удалить её. Это сегодняшнее поведение, регрессии нет.
7. **Объявление говорит о посчитанном, сводка — о черновике.** `setupSummary` остаётся обзором
   черновика (сколько строк заведено), а `setup.calcDone` после успешного расчёта называет числа
   **принятого** `Load` — заказы, позиции и единицы из `toCargoList`. Иначе исключение нулевых
   строк заставило бы объявление врать: «2 позиции» при одной посчитанной.

## Дизайн

### Один источник груза

```
setupState.ts:    toCargoList(orders) → { cargo: CargoType[]; where: Map<cargoTypeId, SetupMessageWhere> }
setupValidation:  engineMessages(orders, vehicle) = validateLoad({ vehicle, cargo }) → SetupMessage[]
```

`toCargoList` становится единственной сборкой груза: её используют `handleCalculate`, Demo и
валидация. Адрес строится **вместе** со списком, а не поиском по `cargoTypeId` после факта — на один
проход меньше и нет соблазна искать по id в другом месте.

**Граница честности адресации.** Уникальность `p.id` гарантирует только `crypto.randomUUID` в
`emptyPosition`; `loadSetup` её не проверяет, поэтому испорченный черновик может дать две строки с
одним id. Карта `cargoTypeId → where` в этом случае сохранит один адрес из двух, и ошибка движка
подсветит не ту строку. Это **не чинится здесь**: уникальность `cargo.id` — предмет `LKWkalk-p3p.15`
(`ERR_DUPLICATE_CARGO_ID` в `validateLoad`), следующей задачи эпика. До неё дубли `p.id` считаются
вне контракта, и спека точной адресации при них не обещает.

Позиции с `quantity === 0` в список не попадают (решение 5); локальные ошибки по ним всё равно
блокируют расчёт (решение 6).

Стратегия (`loadingMode`/`orderGrouping`) в валидации не участвует — `validateLoad` на неё не смотрит.

Стоимость живой валидации: `O(отсеки + позиции × 6)`, количество единиц груза не влияет.

### Тип сообщения

`SetupMessage.code` расширяется до `SetupMessageCode | ValidationErrorCode`. Оба — ключи локалей;
`LoadSummary` уже рендерит `tt(m.code)`, переводы `ERR_*` полные. Ошибка движка с
`details.cargoTypeId` получает `where` и становится кликабельной наравне с локальной; ошибки кузова
и отсеков остаются без адреса — как `volumeOver` сегодня.

### Слияние

```
локальная error по строке            → глушит коды движка по этой же строке
ERR_CARGO_EXCEEDS_VEHICLE по строке  → глушит tooTall по этой же строке
всё остальное                        → показывается как есть
```

Порядок объединённого списка детерминирован: сначала ошибки (локальные, затем движка), потом
предупреждения — иначе «Рассчитать» прыгал бы к разным строкам на одном и том же вводе.

Почему `tooTall` — не дубликат `ERR_CARGO_EXCEEDS_VEHICLE`: локальная проверка смотрит только
исходную высоту, движок — все разрешённые ориентации. Груз с вращением «все 6» ляжет набок: warning
есть, ошибки нет (ADR 013). Совпадают они только при запрете вращения — там warning и прячется.

### Предохранитель в `App` (инвариант, а не удобство)

Гейт в `handleCalculate` не закрывает два обхода: Demo зовёт `onCalculate` напрямую, а
`loadPersistedResult` пересчитывает сохранённый `Load` при старте и проверяет только геометрию.

- `App.onCalculate`: layout с непустым `errors` **не попадает** в `result` — рядом с существующей
  проверкой `findGeometryViolations` и по тому же принципу (доменный инвариант на границе системы).
- `loadPersistedResult`: сохранённый `Load`, дающий ошибки, игнорируется — иначе перезагрузка
  возвращает молчаливый пустой план.
- `onCalculate` возвращает `boolean` — принят результат или нет. Сегодня `setup.calcDone`
  объявляется безусловно сразу после вызова, то есть уже сейчас врёт при геометрическом отказе.
  Объявление делается только по подтверждённому принятию. Причина отказа вызывающему не нужна:
  экран считает ошибки сам, живьём, — поэтому `boolean`, а не структура с ошибками. Смена сигнатуры
  задевает тип пропа, оба вызова (обычный расчёт и Demo) и пустые заглушки `() => {}` в тестах.

**Отказ атомарен и ничего не разрушает.** Показанный план и признак ручных правок переживают отказ:
`setResult` просто не вызывается. Demo меняет форму до вызова `onCalculate`, поэтому отказавший Demo
оставил бы форму и план в разных состояниях — сегодня это недостижимо (все `DEMO_VARIANTS` валидны),
и удерживается тестом-сторожем, что каждый вариант проходит `validateLoad` без ошибок.

### Кнопка и фокус

```
handleCalculate:
  ошибка с адресом    → переход к строке, расчёта нет     (как сейчас)
  ошибки без адреса   → фокус в панель + объявление        (новое)
  ошибок нет          → считаем                            (как сейчас)
```

Гейт стоит **перед** подтверждением сброса ручных правок (`hasManualEdits`): бессмысленно
спрашивать о потере правок, когда расчёт всё равно запрещён. Это сохраняет сегодняшний порядок.

**Новых ключей локалей не нужно.** Шапка уже несёт живую область `setup.header.calcBlocked`
(«Расчёт невозможен: ошибок — N», `role="status"`), которая рисуется при `errorCount > 0` — а после
слияния этот счётчик включает и коды движка. Причины перечислены в панели, в которую уходит фокус.
Заводить второй текст об одном и том же состоянии не нужно.

Панель сводки рендерится в **двух местах**: на широком экране внутри `RulesPanel`, на узком —
отдельно под списком. Ref фокуса обязан попасть в видимый экземпляр, иначе фокус уйдёт в
несмонтированный узел.

### Правка формулировок

Две фразы расходятся с движком: `ERR_INVALID_NESTING` говорит «от 0», движок требует `> 0`;
`ERR_INVALID_COMPARTMENTS` говорит о положительных координатах, хотя `x = 0` законен. Обе поправить
в `de` и `ru`.

## Тесты (сначала красные)

`setupValidation.test.ts` — по кейсу на правило:
- груз длиннее отсека → адресуемая ошибка движка в списке;
- высокий груз с вращением «все 6» → только `tooTall`, ошибки нет;
- он же с запретом вращения → `ERR_CARGO_EXCEEDS_VEHICLE`, `tooTall` спрятан;
- пустая строка → одно `dimsMissing`, `ERR_INVALID_DIMENSION` подавлены;
- неверный шаг вложения → `stepInvalid`, `ERR_INVALID_NESTING` подавлен;
- длина отсека 0 → безадресный `ERR_INVALID_COMPARTMENTS`;
- дубль Auftrags-ID + ошибка движка на той же строке → предупреждение о дубле выжило;
- нулевая позиция с габаритами больше кузова → расчёт не блокируется;
- нулевая позиция с незаполненными размерами / неверным шагом → **блокирует** (решение 6);
- все позиции нулевые → `ERR_EMPTY_LOAD`.

`SetupScreen.test.tsx` — гейт проверяется **наблюдаемым поведением**, а не повторением
production-формулы в тесте (повтор формулы зеленел бы и при расхождении самой сборки):
- адресуемая ошибка движка → ни одна из двух кнопок «Рассчитать» не зовёт `onCalculate`;
- безадресная ошибка движка → то же самое;
- предупреждение при хотя бы одной активной строке → расчёт идёт;
- принятый `Load` не содержит нулевой строки (проверяется по аргументу `onCalculate`);
- `hasManualEdits` + ошибка движка → нет ни `confirm`, ни `onCalculate`;
- отказ не объявляет `setup.calcDone`; успех объявляет числа принятого `Load`, а не сводки;
- фокус в панель — отдельно для широкого и узкого режима.

`App.test.tsx`:
- `onCalculate` с невалидным `Load` не кладёт результат в состояние;
- отказ **не разрушает уже показанное**: план построен, правки внесены вручную, попытка посчитать
  ошибочную заявку — прежний план и признак ручных правок на месте (тест «результата нет» из
  пустого состояния прошёл бы и при неверной очистке);
- сохранённый `Load` с ошибками не восстанавливается: состояние пусто, оба ключа
  (`ladungsplaner.load`, `ladungsplaner.orderColors`) удалены, а черновик «Настройки» и сохранённая
  стратегия — сохранены.

`demo.test.ts` — сторож: каждый `DEMO_VARIANT` проходит `validateLoad` без ошибок (иначе Demo
оставит форму и план в разных состояниях).

## Что задевается из существующего

- **Тест «предупреждение расчёт не блокирует»** (`SetupScreen.test.tsx:609`) держит единственную
  позицию с количеством 0. По решению 5 её `Load` становится пустым, и расчёт блокируется по
  `ERR_EMPTY_LOAD`. Тесту нужна вторая, непустая позиция — иначе он проверяет не то, что называет.
- **Всё, что читает `load.cargo`, перестаёт видеть нулевые строки:** разбор по заказам и легенда
  (`orderBreakdown`), список заказов плана (`orderIndexMap`), PNG, печать и JSON-экспорт — они
  сериализуют принятый `Load` буквально. Это и есть смысл решения 5: нулевая строка исключена из
  заявки, а не «запрошена в количестве 0». Черновик на «Настройке» её по-прежнему показывает —
  граница между черновиком и активной заявкой проходит по `toCargoList`.
- **Заказ целиком из нулевых строк** исчезает из плана, но остаётся в `ladungsplaner.orderColors`:
  `buildOrderColors` строится по всем заказам. Лишний ключ рендеру не мешает (карта читается по
  `orderId`), поведение принимается как есть.
- **Буфер стопок, ручные правки и счётчики по отсекам не задеты**: они работают с `placements` и
  `unplaced` того же принятого `Load`, а не со списком строк черновика.
- **Объявление `setup.calcDone`** сохраняет формулировку и все три подстановки (`orders`,
  `positions`, `units`) — меняется только источник чисел: принятый `Load` вместо сводки черновика.
  Ключ и словари не трогаются, тестов на его числа сегодня нет.
- `ERR_EMPTY_LOAD` достижим (заказ с `positions: []` проходит `loadSetup`) — из набора кодов не
  исключается и показывается как обычная ошибка.

## Вне объёма

- Подстановка `details` в текст (какое поле, какой отсек) — требует параметризованных ключей
  локалей; отдельная задача.
- Нормализация испорченных сохранённых черновиков (заказ без позиций, дубли `p.id`) — здесь только
  показывается ошибка, данные не чинятся.
- `ERR_INVALID_ROTATION` недостижим с этого экрана; спец-случаев нет, появится — покажется как есть.
- **Правка после финального ревью (Minor 6): `ERR_INVALID_QUANTITY` ДОСТИЖИМ.** `Measure`
  (`apps/web/src/ui/primitives.tsx`) — `type="number"` без `min`, поэтому введённое отрицательное
  количество проходит `numOr0` без изменений и доезжает до `toCargoList` (`numOr0(-5) !== 0`, строка
  решением 5 не исключается) — движок отдаёт адресуемый `ERR_INVALID_QUANTITY`. Поведение
  корректное: раньше был молчаливый пустой план, теперь видна причина. Спец-случая в коде не
  требуется — код показывается как обычная ошибка, наравне с остальными.
- **Серверная граница** — `POST /api/plans` сохраняет layout с `errors` как успешный план
  (`apps/server/src/routes/plans.ts`). Та же болезнь, другая поверхность: отдельная задача
  `LKWkalk-559`. Ни один экран сегодня этот путь не вызывает.
- **Уникальность `cargo.id`** — `LKWkalk-p3p.15`, следующая задача эпика; до неё дубли `p.id` вне
  контракта (см. «Граница честности адресации»).
