# Спека: deep-link импорта заказа (`?order=SO-####`) в экран «Настройка» (`LKWkalk-s17`)

Дата: 2026-08-06 · Задача: `LKWkalk-s17` (P2) · Предшественники: `LKWkalk-uvf` (сервер: адаптер
ERPNext + `/api/orders` + guard), `LKWkalk-gxp` (экран «Настройка»), `LKWkalk-p3p.16` (сообщения
экрана)

## Предмет

Логист открывает `https://ladungsplaner.holz-schaefer.de/?order=SO-1234` (ссылка из ERPNext) и
попадает на «Настройку» с уже заведённым заказом: позиции, количества, а где ERPNext дал габариты —
и габариты. Серверная часть готова и не меняется: `GET /api/orders/:id` отдаёт `OrderZone`,
`DataProvider.importOrder` объявлен и реализован в `HttpDataProvider`.

**Клиентская часть не подключена нигде:** `importOrder` в `apps/web` сегодня не зовёт ни один экран,
а обработки URL в приложении нет вовсе (`location.search` не читается ни в одном файле).

## Решения владельца

1. **Импорт ДОБАВЛЯЕТ заказ к черновику**, а не заменяет его. Движок и так группирует груз по
   `orderId`, много-заказная загрузка — штатный сценарий, и ничей труд не пропадает.
2. **Ссылка срабатывает один раз.** После успешного импорта `?order=` вычищается из URL, а заказ с
   уже присутствующим `orderId` не импортируется повторно. F5 и повторный клик по ссылке не плодят
   копий и не затирают габариты, вписанные руками, — а вписывают их именно потому, что в ERPNext их
   нет.
3. **Неудачный импорт не мешает работать:** экран открывается как обычно, черновик не тронут, сверху
   — закрываемая заметка с причиной.

## Где живёт импорт

Внутри `SetupScreen`, не в `App`.

`SetupScreen` уже держит `useOptionalDataProvider()` (`SetupScreen.tsx:113`) и владеет состоянием
`orders`. Это и решает главную трудность: `initialOrders` — ленивый монтировочный шов
(`useState(() => initialOrders ?? loadSetup()?.orders ?? …)`, `SetupScreen.tsx:110`), он читается
ровно один раз при монтировании, и засеять его ответом СЕТИ нельзя. Обычным сеттером после ответа —
можно.

Отвергнуто: **`App` ждёт импорт и монтирует экран уже засеянным.** Это задержало бы весь экран ради
заказа, который может и не приехать (503, 500, обрыв сети), и превратило бы штатный запуск без
`?order=` в запуск с лишним состоянием ожидания.

`initialOrders` остаётся тем, чем был, — швом для тестов и демо. Импорт его не трогает.

## Поток

`useEffect` на монтирование, один раз:

| Условие | Что делаем |
|---|---|
| `?order=` отсутствует или пуст | выходим немедленно; обычный запуск не платит ничего |
| заказ с таким `orderId` уже есть в `orders` | запроса НЕТ; `?order=` вычищается |
| `importOrder` вернул зону | заказ добавляется в конец `orders`; `?order=` вычищается |
| `importOrder` бросил | `orders` не тронуты; `?order=` НЕ вычищается (F5 = повтор попытки); показывается заметка |

Вычистка — `history.replaceState(null, '', <URL без order>)`: не создаёт записи в истории, поэтому
«Назад» не возвращает логиста на ссылку, которая уже сработала. Остальные параметры запроса
сохраняются.

Проверка дубля идёт ДО запроса: незачем ходить в ERPNext, чтобы выбросить ответ.

## Отображение зоны в состояние экрана

Чистая функция в `apps/web/src/screens/setup/setupState.ts`, рядом с `emptyOrder`/`emptyPosition`:

```ts
orderStateFromZone(zone: OrderZone, colorIndex: number): OrderState
```

Тестируется без DOM, как и остальное в этом файле.

| `OrderPosition` | `PositionState` |
|---|---|
| `itemName` | `name` |
| `quantity` | `quantity` |
| `length`/`width`/`height` (`undefined` → ) | `''` — то есть «нужен ручной ввод» |
| `itemCode` | `articleCode` |
| — | правила: умолчания `emptyPosition()` |

`colorIndex` — через существующий `nextColorIndex(orders)`; `key` — через `uid()`, как у
`emptyOrder`.

Обоснования:

- **Габариты из ERPNext НЕ лочатся** (`locked` не ставится). `locked` описывает провенанс полей
  артикула из КАТАЛОГА (`ArticleSuggestion.erpFields`, ADR 022), а не строку Sales Order. Залочить —
  значит лишить логиста возможности поправить размер, который в ERPNext заполнили неверно, а
  исправить его в ERPNext он может не успеть.
- **Отдельная «подсветка позиций без габаритов» не пишется.** Строка с пустыми размерами уже даёт
  локальную ошибку «укажите размеры» с адресом, «Рассчитать» к ней прыгает, а счётчик в шапке её
  считает (`setupValidation.ts:140-142`). Импортированные строки попадают в тот же аппарат без единой
  новой строки кода. Формулировка задачи («позиции без габаритов подсвечены для ручного ввода»)
  описывает поведение, которое уже есть.
- **`dimensionsSource` в состояние экрана не переносится.** По комментарию контракта
  (`dto.ts:16-19`) «нужен ввод» выводится из пустых габаритов, а не из этого тега; второй источник
  той же истины разошёлся бы с первым.

## Заметка об ошибке

`role="status"` над списком заказов, с кнопкой закрытия. Текст выбирается по `code` из тела, которое
`HttpDataProvider.req` бросает при `!res.ok`:

| Что пришло | Текст |
|---|---|
| `code === 'ERR_ERPNEXT_UNCONFIGURED'` (503) | «ERPNext не настроен» |
| всё остальное | общий «Заказ `SO-1234` не импортирован», с номером заказа |

**Общая ветка обязательна, а не подстраховка.** У `GET /api/orders/:id` НЕТ ветки 404: неизвестный
заказ роняет `erpnext.importOrder`, и Fastify отвечает 500 своим дефолтным телом
(`{statusCode, error, message}`), где поля `code` нет вовсе. Самый частый сбой — опечатка в номере
заказа — придёт именно так.

Заведена смежная задача на сервер: `/api/orders/:id` должен отвечать 404 `ERR_ORDER_NOT_FOUND` на
неизвестный заказ. В объём `s17` не входит — задача заявлена как клиентская, серверная часть `uvf`
считается готовой.

Все тексты — ключи локалей `de`/`ru` (i18n с первого коммита, CLAUDE.md §3). Номер заказа
подставляется параметром, а не склейкой строк.

## Тесты

**`orderStateFromZone` (без DOM):**

- позиция без габаритов → `length/width/height === ''`;
- позиция с габаритами → числа как есть;
- `itemCode` → `articleCode`, `itemName` → `name`, количество перенесено;
- правила равны умолчаниям `emptyPosition()`; `locked` не выставлен;
- `orderId` зоны становится `orderId` заказа, `colorIndex` — переданный.

**`SetupScreen` с фейковым провайдером** (`?order=` ставится через `history.replaceState` в jsdom):

| Сценарий | Ожидание |
|---|---|
| `?order=SO-1`, провайдер отдаёт зону | заказ на экране; `location.search` без `order`; провайдер звался один раз с `'SO-1'` |
| `?order=SO-1`, в черновике уже есть `SO-1` | провайдер НЕ звался; `?order=` вычищен; черновик не изменился |
| `?order=SO-1`, провайдер бросает `{code:'ERR_ERPNEXT_UNCONFIGURED'}` | заметка с текстом про настройку; черновик не тронут; `?order=` НА МЕСТЕ |
| `?order=SO-1`, провайдер бросает тело без `code` (дефолтная 500 Fastify) | заметка с общим текстом и номером заказа |
| `?order=` отсутствует | провайдер НЕ звался |

**Локали:** новые ключи в `de` и `ru`; полноту проверяет существующий
`dictionaries/completeness.test.ts`.

## Осознанно вне объёма

- **404 `ERR_ORDER_NOT_FOUND` на сервере** — отдельная задача (см. выше). Клиент к ней готов: общая
  ветка заметки покрывает любое тело без `code`.
- **Кнопка «Повторить» в заметке** — при 503 и 500 бесполезна, а при обрыве сети её заменяет F5,
  который повторяет попытку (`?order=` при ошибке не вычищается). Ещё одно состояние UI не окупается.
- **Импорт заказа из интерфейса** (поиск по `searchOrders` + кнопка) — отдельная работа; здесь только
  вход по ссылке.
- **Обновление уже импортированного заказа из ERPNext** — прямо противоречит решению владельца 2.
