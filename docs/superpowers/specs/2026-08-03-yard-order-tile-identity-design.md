# Двор: порядок по «тип × количество» вместо типа груза (`LKWkalk-72g`)

Пользовательский порядок плиток во дворе (`bufferOrder`, задача B прошлой сессии) хранится списком
`cargoTypeId`, а `orderedTiles` разбирает его FIFO-очередью на тип. Следствие: две плитки одного
типа между собой не переставляются — перестановка даёт тот же список строк, `sameOrder` признаёт
жест пустым, и плитка возвращается на место.

На реальном плане владельца двор односортный (136 EPAL 3), то есть заказанная им в прошлой сессии
перестановка на его же данных выглядит сломанной.

## Границы задачи

Владелец (2026-08-03): «если они идентичны — то зачем их переставлять? Не важно, будут ли они
различимы».

- Плитка одного типа и одного количества визуально неотличима от такой же (подпись `EPAL 3 ×17`,
  та же геометрия). Делать их различимыми — **не задача**: перестановка неразличимого не нужна.
- Чинится ровно один наблюдаемый случай: **остаток** (`×12` среди `×17`) сегодня не переставляется
  никуда, хотя на экране он отличается от соседей.
- **Повёрнутая** плитка остаётся непереставляемой: она отличается от соседей визуально, но не по
  ключу. Поворот во дворе существует ради броска в кузов, а не ради места во дворе — цена полной
  идентичности плиток этого не стоит.
- `tileOrientation` и его ключ «тип#вхождение» не трогаются: хрупкость известна и относится к
  повороту, а не к порядку.
- `bayOrder` (порядок загонов, `41e.6`) не трогается. При включённой группировке порядок диктуют
  загоны, и ручная перестановка во дворе уже сегодня — no-op.

## Решения брейншторма

| Вопрос | Решение |
|---|---|
| Идентичность плитки | Нет. Ключ — пара «тип × количество», модель порядка остаётся слоем поверх производного `stackBuffer` |
| Неразличимые плитки | Остаются неразличимыми и непереставляемыми; жест по-прежнему no-op |
| Повёрнутая плитка | Вне задачи |
| Несовпадение нарезки при броске из кузова | Запасной проход по типу — поведение остаётся сегодняшним, не хуже |

## 1. Ключ порядка

```ts
/** Ключ плитки в пользовательском порядке двора: количество впереди, поэтому ПЕРВОЕ двоеточие
 *  делит однозначно при любом `cargoTypeId` (id приходит из пользовательского справочника). */
const orderKey = (t: { cargoTypeId: string; units: number }) => `${t.units}:${t.cargoTypeId}`;
```

Тип состояния не меняется: `bufferOrder` остаётся `string[]`, сброс на новом `layout` — прежний.

## 2. Реконсиляция `orderedTiles` — две фазы

Очереди строятся по `orderKey`, а не по `cargoTypeId`. Для каждого ключа из `bufferOrder`:

1. **точная фаза** — если очередь этого ключа непуста, снять с неё голову;
2. **запасная фаза** — иначе снять голову с первой непустой очереди **того же типа груза**
   (в порядке появления очередей, то есть в порядке `stackBuffer`).

Хвосты всех очередей дописываются в конце в порядке `tiles`, как сейчас: ключ, которого порядок не
упоминает, сохраняет место по умолчанию.

Запасная фаза обязательна, а не «на всякий случай». Буфер пере-нарезается на каждом рендере
(полные стопки по `per`, затем остаток), а бросок из кузова во двор записывает порядок **до** того,
как плитки появятся в буфере, — и предсказанное количество может не совпасть с тем, что выдаст
`stackBuffer`. Пример: во дворе `[×17, ×7]` (24 неразмещённых), из кузова вернули колонну из 5 при
`per = 17` → 29 неразмещённых, буфер выдаст `[×17, ×12]`, а в снимке стоят ключи `7:` и `5:` — ни
один не совпадает ни с чем. Без запасной фазы такой бросок сел бы на место по умолчанию, то есть
задача починила бы остаток и сломала бы уже работающий бросок. С запасной фазой при несовпадении
поведение ровно сегодняшнее — FIFO по типу.

Побочное следствие устройства ключа: тип восстанавливается как всё после **первого** двоеточия, а в
ключе старого вида (голый `cargoTypeId`) двоеточия нет вовсе — такой ключ целиком читается как тип
и попадает ровно в запасную фазу. Порядок, записанный до этой задачи, деградирует до прежнего
поведения сам, без миграции.

## 3. Путь броска из кузова (`onDropOutside`)

`StackRef` — это `{cargoTypeId, x, y}`, количества в нём нет, а снимок порядка теперь требует пару.
Количество единиц колонны берётся из `topRects(load, edited)` — той же группировки по
`cargoTypeId:x:y`, что рисует вид сверху; своей копии правила «колонна = ярусы в одной точке» на
экране не заводим.

Остальное без изменений: снимок текущего порядка → `splice` брошенных ключей в точку релиза →
`setBufferOrder`.

## 4. Путь перестановки внутри двора (`reorderYard`)

Меняется только источник строк: `orderedTiles.map(orderKey)` вместо `.map((t) => t.cargoTypeId)`.
Защита `sameOrder` остаётся на месте и продолжает делать своё дело — перестановка двух
неразличимых плиток даёт тот же список и **ничего не пишет** в состояние, чтобы жест, ничего не
изменивший, не заморозил неявный порядок по умолчанию в явный пользовательский.

## 5. Тесты

Модуль `yardOrder.ts` покрыт модульными тестами (`yardOrder.test.ts`): обе фазы, повторённый ключ,
исчезнувший тип, id с двоеточиями внутри, порядок неупомянутого хвоста при неконтигуозном входе,
сохранение мультимножества. Жесты — на уровне экрана (`LadeplanScreen.test.tsx`), там же, где живут
существующие тесты `bufferOrder`.

Ведущие (сначала падающие):

1. **Остаток переставляется.** Двор `[×17, ×12, ×1]`, перенос `×17` на место третьей плитки →
   `[×12, ×17, ×1]`. До правки падает: список строк не менялся.
2. **Бросок пишет ключ с количеством.** В кузове колонна из 5 при полной стопке 17, во дворе одна
   плитка `×17`. Бросок перед ней → `[×5, ×17]`: ключ `5:` совпадает точно. Со снимком из голых
   `cargoTypeId` точного совпадения нет вовсе, работает запасная фаза, и стопка садится позади.
3. **Регрессия на запасную фазу.** Двор `[×1, ×17, ×7]`, из кузова возвращается колонна из 5 →
   буфер перенарезается в `[×1, ×17, ×12]`, и ключей `5:` и `7:` в нём нет. Возвращённая стопка всё
   равно стоит первой; без запасной фазы получилось бы `[×1, ×17, ×12]` — место по умолчанию.

Границы, запиннены отдельно:

4. **Близнецы не переставляются.** Двор `[×17, ×17, ×1]`: перенос одной `×17` на место другой
   ничего не меняет и ничего не пишет в состояние. Тем же тестом накрыто ограничение про
   ориентацию — повёрнутая плитка среди близнецов тоже неподвижна.
5. Существующие тесты порядка двора (сброс `bufferOrder` на свежем `layout`, бросок в точку релиза,
   порядок загонов) остаются зелёными.

Отдельно — живая проверка в настоящем Chrome (jsdom этого не умеет): кузов на одну колонну,
100 поддонов, двор `[×17, ×17, ×17, ×17, ×15]`; остаток перетаскивается в начало ряда и там
остаётся. Контракт движка (`0.15.0`) не меняется.
