## Что сделано

**`LKWkalk-1f5` — бирка загона читалась заголовком раздела.** Прежние числа (`TAG_H = 330`,
`TAG_W = 2200`, `TAG_PAD = 120`, `BAY_MIN_W = 2400`) задавались «на глаз» в спеке `41e.2`, до того как
загоны увидели в настоящей заявке. Мера переставлена **со строки на груз**: `TAG_W = 1200` (длина
европоддона), `TAG_H = 180` (четверть его глубины), `TAG_PAD = 70`, `BAY_MIN_W = 1200 + 2·BAY_PAD`.
Ключевое соотношение, которое теперь пинит тест: кегль бирки (`TAG_H · 0.62 ≈ 111`) **мельче**
счётчика `×N` на самой стопке (`vehicle.width · 0.05 ≈ 124`) — бирка вторична по отношению к грузу.
Инвариант `BAY_MIN_W > TAG_W` сохранён (1600 > 1200), поэтому обрезка плашки по ширине загона осталась
страховкой, а не рабочей веткой.

**`LKWkalk-8z2` — порядок загонов уезжал за историей перетаскиваний.** `groupByOrder` брал порядок
групп по первому появлению в списке **плиток**, а плитки приходят из `stackBuffer` поверх
`bufferOrder`. Теперь порядок берётся из `load.cargo` — из заявки, то есть из первоисточника, а не из
производной. Порядок плиток **внутри** загона остался дворовым (там броском двигают именно стопки),
`bayOrder` (`41e.6`) по-прежнему перекрывает умолчание, заказ без стопок во дворе загона не открывает.

**`LKWkalk-jen` — сценерия росла вместе с буфером.** Доки масштабировались по высоте пола, то есть
занимали 100% глубины двора. `WarehouseBackdrop` получил **обязательный** `dockHeight` — постоянную
меру двора (минимальная глубина = ширина кузова); доки ограничены по высоте и прижаты к верху, лишняя
глубина остаётся асфальтом. `Math.min(dockHeight, height)` — страховка, чтобы док не вылез за мелкий
двор.

## Решения и поздние находки

1. **Мера берётся у груза, а не «под строку».** Прежний `TAG_W = 2200` был подобран под конкретную
   строку `SO-1042 · ×18`; такая мера ничем не ограничена сверху и растёт вслед за самым длинным
   номером. Европоддон 1200×800 — единица масштаба двора, и от неё уже выводятся все три числа.
2. **`dockHeight` — обязательный проп, а не «по умолчанию `height`».** Умолчание вернуло бы ровно ту
   зависимость от содержимого, из-за которой сценерия и разъезжалась. Это моё решение, не владельца.
3. **Поздняя находка ревью:** дедуп ключей заявки шёл через `keys.includes` в цикле по `cargo`
   (O(n²)); заменён на `Set` — тем же приёмом, что рядом для `bayOrder`.
4. **Долг из PR #37, подобранный заодно:** док-комментарий `WarehouseFloorLayout.width` утверждал
   «always the vehicle length», хотя с `6n4` ширина двора = `truckFrame(...).outerW`. Ревьюер писал об
   этом ещё неделю назад; правка доехала только сейчас.
5. **Наезд разметки на доки по горизонтали НЕ чинился** — вынесен в `LKWkalk-103` (варианты: отдать
   ~1.4 м ширины ряда, опустить сценерию, или признать в спеке). Решение за владельцем.

## Грабли

1. **⚠️ Уменьшение константы может сделать тест вакуумным, и он останется зелёным.** `BAY_MIN_W`
   2400 → 1600 обнулило смысл теста «загоны переносятся на новую строку»: при `width: 6000` второй
   загон стал влезать, и тест проверял бы перенос, которого нет. Пришлось перепараметризовать ширину
   (6000 → 5000). **Меняя геометрическую константу, перечитай тесты, которые её НЕ упоминают.**
2. **⚠️ CDP: `Page.captureScreenshot` с `captureBeyondViewport: true` клипует в координатах СТРАНИЦЫ,
   а `getBoundingClientRect()` отдаёт координаты вьюпорта.** Первый снимок уехал на полторы тысячи
   пикселей вверх и показал совсем другую секцию. Лечится `r.x + scrollX`, `r.y + scrollY`.
   (Прошлая сессия наступила на смежную грабку: `Input.dispatchMouseEvent` — наоборот, во вьюпорте.)
3. **Состояние приложения для проверки проще СЕЯТЬ, а не накликивать.** `localStorage`:
   `ladungsplaner.load` (весь `Load` как JSON) + `ladungsplaner.yardGrouping` (`'true'`/`'false'`),
   затем перезагрузка страницы — план восстанавливается из `Load` через `calculateLayout`.
   Скрипт этой сессии лежал в скретчпаде и в репозиторий не попал.
4. **Флейк `LKWkalk-w9j` кусается в РАЗНЫХ тестах `SetupScreen.test.tsx` от прогона к прогону**
   (в этой сессии — три разных набора). Правило прежнее и подтвердилось: засчитывать падение только в
   ОДИНОЧНОМ прогоне файла (`npx vitest run apps/web/src/screens/SetupScreen.test.tsx` → 66/66).
5. `apps/server` локально красен — `better-sqlite3` под другой ABI (`NODE_MODULE_VERSION 137 vs 127`),
   5 файлов / 35 тестов. Пре-существующее, в CI на чистом Node зелено. Подтверждено и в этой сессии.
6. **⚠️ `gh pr merge` может быть заблокирован классификатором разрешений** — это не ошибка GitHub и не
   красный CI. Обходить нельзя; мержит владелец либо выдаёт разрешение.
