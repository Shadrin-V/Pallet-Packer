## Что сделано

**`LKWkalk-6n4` — масштаб 1:1 двора и кузова восстановлен.** Стопка во дворе была крупнее той же
стопки в кузове на 11–23% — тем сильнее, чем короче кузов (Wechselbrücke 7150 — 23%, 13,6 м — 11%).

Корень не в арифметике, а во владении числом: `outerW = frontGutter + length` считал `CrossSection`,
а инвариант «мы одной ширины» держал `WarehouseFloor` — **комментарием**. `41e.1` добавила поле под
кабину, и обещание умерло молча.

- **`truckFrame.ts`** (новый, чистый) — единственный владелец рамки: `frontGutter`, `topGutter`,
  `wheelGutter`, `outerW`, `outerH`. `CrossSection` и `warehouseLayout` берут числа оттуда.
- `warehouseFloor()` по умолчанию шириной `truckFrame(vehicle,'top').outerW`, а не `vehicle.length`.
- **`holdYardScale.test.tsx`** — кросс-компонентный тест: рендерит оба svg и требует равенства ширин
  внешних `viewBox`. Единственный тест, который пинит само обещание.
- Удалён мёртвый `GUTTER.ruler`; исправлен комментарий `0.657` → фактические `0.618`.

**`LKWkalk-ku5` — решения зафиксированы, реализация ждёт арта.** Корень найден и он не в коде: в
референсе владельца в `<desc>` написано *«minimized cab and wheels»* — вектор намеренно НЕ в масштабе
(колесо ~530 мм вместо ~1050, пол в ~370 мм над землёй вместо ~1150). Решения: чертёж в масштабе +
разная ходовая под тип шасси; вид сбоку обрезает колёса по линии осей; тип шасси живёт **в UI, не в
контракте ядра**; арт — векторы владельца, не рукописный SVG.

## Решения и поздние находки

1. **Двор занимает полосу под кабиной стопками** (выбор владельца из двух вариантов). Цена принята:
   полный ряд во дворе больше НЕ означает «этот ряд влезет в кузов». Выигрыш — двор использует всю
   карточку и меньше растёт вглубь.
2. **Тестов с явной шириной оказалось три, а не два** (план предвидел два). Третий — про перенос
   **загонов**, а не плиток: он тоже сужал кузов, чтобы вызвать перенос, и с широкой рамкой перестал.
   Правило: где ширина — инструмент, а не предмет проверки, её задавать опцией `width`.
3. **Тип шасси НЕ идёт в контракт ядра** — он не влияет на упаковку. Живёт в состоянии `apps/web`;
   экспорт PNG/PDF получает его бесплатно, потому что рендерит тот же DOM.
4. **ТЗ на арт описывают процесс из четырёх шагов**, потому что рисовать будет ИИ: растровый
   техчертёж → правки → трассировка по математическим правилам → сверка готового SVG по числам с
   возвратом на нужный шаг. Условия, которые трассировкой не лечатся (пустая грузовая область, ничего
   поверх короба, пустая середина, оба вида одной картинкой ради 1:1, ортогональность), стоят в
   ПЕРВОМ промпте.

## Грабли

1. **⚠️ Счётчик тестов из полного прогона — НЕ гейт.** Набор нестабилен под нагрузкой: два прогона
   подряд роняли РАЗНЫЕ пары тестов. Замерено на чистом `main` (`d65c89f`, отдельный ворктри): он
   роняет 2 теста `SetupScreen` **без единой правки**. Строка «617 зелёных» в прошлом handover —
   удачный прогон, а не гарантия. **Правило: падение засчитывать, только если тест валится в
   ОДИНОЧНОМ прогоне своего файла** (`npm test -- App.test` → 18/18 при красном полном прогоне).
   Заведено в `LKWkalk-w9j`.
2. **⚠️ Проверять выкладку по CSS-ассету — ненадёжно.** Прошлый handover советовал `grep` по
   `/assets/*.css`. Но эта сессия не трогала стили, CSS-бандл побайтово тот же → **хеш не изменился**,
   хотя деплой прошёл. Сменился JS: `index-D_e2Z1IG.js` → `index-Ex4csgno.js`. Сторожить надо **любой**
   ассет, а лучше JS: `curl -s <site>/ | grep -o '/assets/index-[^"]*\.\(css\|js\)'`. Монитор,
   настроенный только на CSS, не сработал бы никогда.
3. `npm test -w apps/web` НЕ СУЩЕСТВУЕТ (у `apps/web` и `packages/i18n` нет своего скрипта `test`).
   Фильтром пути от корня: `npm test -- apps/web packages`.
4. `apps/server` локально красен — `better-sqlite3` под другой ABI (`NODE_MODULE_VERSION 137 vs 127`),
   ~32 падения. Пре-существующее, в CI на чистом Node зелено.
5. `gh pr merge --delete-branch` ломает локальный `checkout` при грязном `.beads/issues.jsonl`. В этой
   сессии обошёл: `gh pr merge --squash` без флага, затем `git checkout main && git pull --ff-only`,
   ветку удалил руками.
6. `bd remember --get` не существует; читать память — `bd memories <keyword> --json`.
