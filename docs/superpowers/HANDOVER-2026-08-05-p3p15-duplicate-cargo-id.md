## Что сделано

`validateLoad` не отвергал `Load`, где два элемента `cargo` делят один `id`. Движок группирует
размещения и остатки по `cargoTypeId` (`getLayoutReport`, колонки метрик, остатки упаковщика),
поэтому второй элемент с тем же id молча портил счётчики первого — «запрошено / размещено / не
размещено» врали без единого сообщения.

| Слой | Стало |
|---|---|
| Ядро | Код `ERR_DUPLICATE_CARGO_ID`, `details: { cargoTypeId, count }`; по одной ошибке на каждый задвоенный id, на первом его вхождении |
| Порядок | Проверка стоит после `ERR_EMPTY_LOAD` и до построчного цикла |
| Локали | de/ru + расширен гейт полноты словарей |
| Экран | Продакшн-кода не потребовалось — `engineMessages` адресует строке любой код с `details.cargoTypeId`; добавлены тесты доставки |

## Решения

- **Защита только в ядре.** Самолечение испорченного черновика в `loadSetup` (перевыдача uuid при
  загрузке) отвергнуто владельцем: оно прячет порчу данных и заводит второй скрытый путь правки
  состояния, а входы API/MCP всё равно требуют проверки в ядре.
- **По одной ошибке на каждый задвоенный id** — не одна на весь `Load` (как у отсеков) и не по одной
  на каждое повторное вхождение: `cargo` — заявка из многих строк, остальные её проверки построчные,
  а вхождения одного id адресом не различаются (`addressOf` хранит один адрес на id).
- **Сравнение точное, без `trim`** — намеренно иначе, чем локальная проверка дубля Auftrags-ID. Для
  движка `id` — ключ группировки как есть: `"a"` и `" a "` дают разные колонки и работают корректно.
- **Бамп `0.17.0` → `0.18.0`** аддитивен по форме, но по поведению это **ужесточение**: такой `Load`
  раньше принимался. Ломающим не считается — принимался он с молча испорченными счётчиками.
- **Две принятые границы:** адрес ведёт к последнему вхождению (чинится удалением любой из двух
  строк); локальная ошибка той же строки глушит код о дубле по правилу слияния из `p3p.16` — расчёт
  всё равно заблокирован, молчаливого успеха нет.

## Грабли

1. **Order-insensitive утверждение не закрепляет порядок, от которого зависит поведение.** Место
   вызова проверки — load-bearing: от порядка ошибок зависит, к какой строке прыгает «Рассчитать».
   Единственный тест, где код о дубле встречался с построчным кодом, использовал
   `expect.arrayContaining`; ревьюер физически передвинул вызов в конец `validateLoad` — **28/28
   остались зелёными**. Лечение: `toEqual` с точным массивом кодов. Обобщение: мутационное
   доказательство ставить не только на «работает ли фича», но на КАЖДОЕ свойство, которое спека
   называет важным. Приём, который это поймал: не читать тест, а переставить производственную строку
   и посмотреть, покраснеет ли suite.
2. **У воркспейсов нет скрипта `test`** — vitest объявлен только в корневом `package.json`. План
   предписывал `npm test --workspace @shadrin-v/i18n`; команда падает с `Missing script: "test"`, а
   исполнитель выдал корневой прогон за scoped. Поймал ревьюер, попытавшись повторить команду.
   Точечный прогон — путём: `npm test -- <путь>`.
3. **Число падающих тестов в плане надо считать, а не прикидывать.** План обещал «упадут пять»,
   упали четыре: два теста из шести — guard'ы (пробелы в id, уникальные id), они зелены и без
   производственной строки, потому что стерегут отсутствие ложных срабатываний.
4. **Кросс-пакетный гейт диктует порядок задач.** `setupValidation.test.ts` требует, чтобы каждый
   `VALIDATION_ERROR_CODES` был в `TRANSLATION_KEYS`, поэтому ключ локали обязан лечь ДО кода
   движка. Обратной зависимости нет: лишний ключ перевода не ломает ничего (прецедент
   `ERR_UNKNOWN_VEHICLE`).
