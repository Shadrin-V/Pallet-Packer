# ADR 026 — Транспорт с несколькими отсеками: интервалы на общей оси, а не `compartmentId`

- **Статус:** принято (2026-08-04)
- **Контекст задачи:** эпик `LKWkalk-p3p` (автопоезд)
- **Контракт:** `0.16.0` (аддитивно)
- Связано: [ADR 003](003-2p5d-computation-model.md) (модель расчёта 2.5D),
  [ADR 017](017-dense-floor-heuristic.md) (плотная напольная эвристика),
  [ADR 019](019-manual-layout-editing-api.md) (алгебра ручных правок),
  [ADR 020](020-magnet-drop-resolution.md) (магнит постановки),
  [ADR 024](024-slide-to-stop.md) (упор)

## Контекст

Со схемы логиста ([справочник](../lkw-presets-logist-2026-07-20.md), вариант 5) есть автопоезд:
15 400–16 000 мм при ширине 2450 и высоте 3050, 110–120 м³. Внести его пресетом было нельзя:
`Vehicle` — это одни внутренние размеры, поэтому единый отсек длиной 15,4 м разрешил бы упаковщику
поставить поддон **в разрыв между тягачом и прицепом**, где нет пола. Вариант 5 по этой причине был
осознанно отложен владельцем 2026-07-20 (см. справочник пресетов) и заведён отдельной задачей
`LKWkalk-p3p`.

Нужна модель нескольких грузовых отсеков — сквозная: упаковщик, метрики, ручная правка,
визуализация, отчёт. Владелец на брейншторме (2026-08-04) зафиксировал: одна заявка на весь
автопоезд, движок сам делит груз между кузовами; заказ может разъехаться по двум кузовам, если не
влез целиком; ручная правка — внутри отсека, перекинуть стопку между кузовами — только через двор;
длины отсеков — по полю на каждый, добавлять/удалять отсеки нельзя; чертёж — один рисунок с видимым
разрывом, а не блок на каждый кузов.

Последний пункт — решающий для формы контракта.

## Решение

**Отсек — интервал `[x, x + length)` на общей оси длины транспорта.** `Vehicle.length` — это
по-прежнему полный пролёт по длине, включая разрывы; `compartments?: Compartment[]` перечисляет
отсеки по возрастанию `x`. Разрыв между машинами не выделен отдельной сущностью — это просто
промежуток координат оси, не покрытый ни одним отсеком.

```ts
interface Compartment {
  id: string;
  name?: string;   // ключ метки; локализация — на стороне UI
  x: number;       // мм, начало отсека по оси длины; целое, >= 0
  length: number;  // мм, > 0, целое
}

interface Vehicle {
  id: string;
  name: string;
  length: number;  // полный пролёт по длине, ВКЛЮЧАЯ разрывы между отсеками
  width: number;
  height: number;
  compartments?: Compartment[];   // отсутствует = один отсек [0, length)
  maxPayload?: number;
}
```

Автопоезд: `compartments = [{x: 0, length: 7700}, {x: 8900, length: 7700}]`, `length = 16600`.
Интервал 7700…8900 — физический разрыв: координаты там существуют, груз туда не встаёт.

**Сквозной инвариант, заменяющий проверку габаритов кузова:** единица груза лежит целиком внутри
**одного** отсека — не «в габаритах кузова», а «в габаритах отсека». Это запрещает и постановку в
разрыв, и стопку, оседлавшую границу машин; проверяется там же, где сегодня стоит проверка границ:
`findGeometryViolations`, `moveStack`/`placeStack`/`moveStacks`, `resolveDrop`, `resolveSlide`.

**Метрики считаются суммой по отсекам.** Сегодня объём кузова — `length × width × height`. С
разрывом это завысило бы кузов на пустоту, которой физически нет, и занизило бы
`volumeFillPercent`. Поэтому:

```
floorArea  = Σ (отсек.length × width)
holdVolume = floorArea × height
```

Для односоставного кузова (без `compartments`) обе формулы дают ровно прежнее число — это и делает
изменение аддитивным на уровне поведения, а не только на уровне форм.

**Новый код ошибки — один:** `ERR_INVALID_COMPARTMENTS` (пустой массив при наличии поля; `x`/`length`
не целые, `length ≤ 0`, `x < 0`; отсеки не по возрастанию `x` или пересекаются; конец последнего
отсека ≠ `vehicle.length`). Пустой массив невалиден намеренно: односоставный кузов выражается
**отсутствием** поля, чтобы у одного состояния не было двух представлений. `ERR_CARGO_EXCEEDS_VEHICLE`
меняет смысл: груз великоват, если не влезает **ни в один** отсек в любой разрешённой ориентации —
восьмиметровая деталь в автопоезд 2 × 7,7 м не помещается, хотя формально короче полного пролёта
16,6 м.

## Почему интервалы, а не `compartmentId` с локальными координатами

Отвергнутая альтернатива — дать `Placement` и `StackRef` идентификатор отсека и считать координаты
от угла каждого отсека, а не от угла транспорта. На первый взгляд она честнее: у каждой единицы
явно написано, в каком она кузове.

| | Разрыв на общей оси | `compartmentId` + локальные координаты |
|---|---|---|
| `Placement`, `StackRef`, `PlaceStackSpec`, `DropResolution`, `GroupAim`, `SlideDelta` | не меняются | у каждого появляется поле отсека |
| Контракт | аддитивно, `0.16.0` | ломающее: мажорная версия + синхронная правка всего UI |
| Пиксельная математика UI | не меняется | переписывается |
| Чертёж «один рисунок с разрывом» (решение владельца) | получается сам собой | нужно собирать N вложенных SVG и сшивать их обратно в одну картинку |

Решающий довод — устройство чертежа, а не вкусовщина по формам типов. Область броска в
`CrossSection` — это **одна вложенная** `<svg data-hold>` с `viewBox="0 0 length spanY"`; через
`getScreenCTM` она отображает клиентские пиксели прямо в миллиметры груза, и `LadeplanScreen`
пересчитывает через неё же броски из двора в кузов. Пока ось длины одна, `toSvg`, призрак переноса,
бросок двор→кузов, PNG-экспорт и линейка не трогаются вовсе — им без разницы, сколько отсеков стоит
на этой оси, они видят только миллиметры. С локальными координатами эта единственная система
координат распадается на N: нужно было бы либо завести N вложенных `<svg>` (каждая — свой
`getScreenCTM`, свою зону броска, свою логику «в какой из них сейчас курсор»), либо тащить в UI
знание о границах отсеков и переводить пиксели в мм вручную — второе место, знающее геометрию
транспорта, чего и без того избегает принцип №1 (CLAUDE.md).

Цена интервалов на общей оси — это не отсутствие цены, а цена, перенесённая туда, где она дешевле:
упаковщику и алгебре правок приходится на каждой проверке границ спрашивать «в каком отсеке лежит
эта точка» вместо того, чтобы читать это напрямую из `StackRef`. Это O(число отсеков) — на автопоезде
из двух штук неотличимо от константы — и вопрос уже встаёт в тех же местах, где сегодня стоит
проверка «в кузове ли». Локальные координаты сэкономили бы этот единственный поиск ценой
переписывания всей пиксельной математики UI ради данных (номер отсека), которые упаковщику всё
равно не нужны: раскладка задачи не о том, «в каком кузове» единица, а о том, «пересекается ли она с
соседями» — а для этого нужны координаты на одной оси, не две системы отсчёта.

Задача поэтому **перестаёт быть ломающим изменением контракта**, вопреки исходной формулировке в
`bd` и в справочнике пресетов ([`docs/lkw-presets-logist-2026-07-20.md`](../lkw-presets-logist-2026-07-20.md)).

## Последствия

- Контракт `0.16.0`, аддитивно: новый тип `Compartment`, поле `Vehicle.compartments?`, код
  `ERR_INVALID_COMPARTMENTS`. Формы `Placement`, `StackRef`, `PlaceStackSpec`, `Layout`,
  `DropResolution`, `SlideDelta`, `BufferStack` не меняются ни на поле.
- Отсутствие `compartments` = один отсек `[0, length)` = сегодняшнее поведение, побайтово — это
  главный страховочный тест будущей реализации (задача 2 эпика).
- Упаковщик (`packages/engine/src/packing/orchestrator.ts`) получает внешний цикл по отсекам;
  внутренняя логика зон заказов (`packFloor`, `computeVerticalStack`, `columnPlacements`) не
  меняется — она и так пакует прямоугольную область. Приоритет заявки (порядок `cargo`, ADR 017) и
  смежность зон заказов (ADR 011) сохраняются внутри каждого отсека; заказ, не поместившийся в
  первый, продолжается в соседнем.
- `Layout` не получает счётчиков по отсекам — «в тягаче N, в прицепе M» UI строит сам, разложив
  `placements` по интервалам `compartments`; хранить это в контракте незачем, это и есть выигрыш
  общей оси.
- Ручная правка, магнит (ADR 020) и упор (ADR 024) не получают новых операций и новых кодов ошибок:
  меняется одна проверка границ — с «в кузове» на «в каком-нибудь отсеке целиком». Отказ по-прежнему
  идёт существующим `ERR_EDIT_OUT_OF_BOUNDS`.
- Будущий MCP-инструмент видит `compartments` как обычное опциональное поле `Vehicle` — без нового
  инструмента и без рефакторинга ядра.
- Разрыв (1200 мм) и длины отсеков (7700 + 7700) со схемы логиста правдоподобны, но не сняты с
  реальной машины; пометка «требует подтверждения логистом» остаётся в `docs/spec.md` (Приложение A)
  и в справочнике пресетов до уточнения.

## Альтернативы

- **`compartmentId` + локальные координаты в `Placement`/`StackRef`.** Отвергнуто — разбор выше:
  ломающая мажорная версия контракта, синхронная правка всего UI и потеря единственной системы
  координат, на которой стоит вся пиксельная математика `CrossSection`, ради данных, не нужных
  упаковщику.
- **Хранить разрыв как отдельное поле (`gapAfter`/`gaps: number[]`), а не выводить его из
  промежутков между отсеками.** Отвергнуто: завело бы два источника истины про одну и ту же
  геометрию — `compartments[i].x + compartments[i].length` и отдельно записанный зазор могли бы
  разойтись. Требование «конец последнего отсека = `vehicle.length`» и проверка неперекрытия/
  неубывания `x` в `ERR_INVALID_COMPARTMENTS` держат `length` и разрывы честно производными от одной
  структуры.
- **Оставить единый отсек и просто не давать упаковщику ставить в зону разрыва через отдельный
  список «запретных прямоугольников».** Отвергнуто ещё на этапе брейншторма: это решило бы только
  постановку, но не деление груза на «в тягаче»/«в прицепе» для отчёта, не второй проход упаковки для
  заказа, продолжающегося в соседнем кузове, и не редактор с полем длины на каждый отсек — то есть
  не закрыло бы задачу `LKWkalk-p3p` целиком, а только один её угол.
